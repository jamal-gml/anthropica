# Instruction file template and layout

## Where things go
| Content | Location |
|---|---|
| Project-wide facts, commands, conventions, safety rules | root `CLAUDE.md` (or `AGENTS.md` imported by `CLAUDE.md`) |
| Rules for one area (frontend, migrations, infra) | `<dir>/CLAUDE.md` (loaded when working there) or `.claude/rules/<topic>.md` |
| Repeatable multi-step procedures (release, add endpoint) | `.claude/skills/<name>/SKILL.md` |
| Personal preferences, local paths, sandbox URLs | `CLAUDE.local.md` (add to `.gitignore`) or user-level `~/.claude/CLAUDE.md` |
| Shared tool permissions, hooks | `.claude/settings.json` (personal: `.claude/settings.local.json`, gitignored) |
| Long reference docs | `docs/...`, linked or imported with `@docs/file.md` only if always needed |

Imports (`@path/to/file`) load the whole file every session; prefer a plain link with "read X when Y" for situational material.

## Root CLAUDE.md template
Delete any section that would be empty or generic. Keep it under ~100 lines.

```markdown
# <Project name>

<One or two lines: what this is and who uses it.>

## Commands
- Install: `<cmd>`
- Dev server: `<cmd>`
- Test all: `<cmd>`; single file/test: `<cmd>`
- Lint / format / typecheck: `<cmd>` / `<cmd>` / `<cmd>`
- Before committing run: `<cmd>`
- Codegen / migrations: `<cmd>` (not verified)

## Architecture
- `<path>` - <responsibility>  (only the 3-8 entry points that matter)
- Request flow: <route -> service -> repository>, see `<exemplar file>`
- Data: <DB engine>, migrations in `<path>`, created with `<tool>`

## Conventions
- <rule that differs from ecosystem default>, e.g. "Errors: throw `AppError` subclasses; never return null for not-found" - see `<file>`
- Tests live next to code as `*.test.ts`; use factories in `<path>`, not inline fixtures
- Imports: <alias rules>

## Gotchas
- <non-obvious fact that caused mistakes>, e.g. "`src/gen/` is generated by `<cmd>`; never edit by hand"
- <ordering>, e.g. "Run codegen before typecheck after changing `schema.graphql`"
- <environment>, e.g. "Integration tests need `docker compose up db`"

## Rules
- Never edit applied migrations; add a new one
- Ask before adding dependencies, changing public API contracts, or touching `<sensitive path>`
- Branches `<prefix>/<slug>`; commits follow Conventional Commits
```

## Good vs bad lines
| Bad (generic or vague) | Good (specific, testable) |
|---|---|
| Follow best practices for React. | Components are function components in `src/components/<Name>/index.tsx`; co-locate `*.test.tsx`. |
| Make sure tests pass. | Run `pnpm vitest run <file>` for the file you changed, then `pnpm check` before committing. |
| The project uses a database. | Postgres 16; schema source of truth is `db/migrations/`; never use `synchronize: true`. |
| Be careful with config. | `config/prod.yaml` is deployed as-is; changes need review from the platform owner. |
| IMPORTANT!!! NEVER EVER ... (shouting everywhere) | Reserve emphasis for the one or two rules that are truly critical. |

## Trimming an existing bloated file
1. Run the commands it lists; delete or fix the ones that fail.
2. Delete lines Claude would follow anyway, and lines describing what the code already shows.
3. Move area-specific sections to subdirectory files or rules; move procedures to skills.
4. Replace pasted docs with links.
5. Present the before/after line count and the diff for approval.

## AGENTS.md
Cross-tool convention read by several coding agents. When the repo uses more than one agent tool:
- Put shared content (commands, conventions, gotchas) in `AGENTS.md`.
- Make `CLAUDE.md` a short file: `@AGENTS.md` plus Claude-specific notes (skills, hooks, settings).
- Keep tool-specific rule folders minimal and pointing at the shared file.

## settings.json starter (shared, safe)
```json
{
  "permissions": {
    "allow": ["Bash(npm run lint)", "Bash(npm test:*)", "Bash(git status)", "Bash(git diff:*)", "Bash(git log:*)"],
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
  }
}
```
Adjust commands to the project. Never add allow rules for deploy, publish, `rm -rf`, force push or production database access.
